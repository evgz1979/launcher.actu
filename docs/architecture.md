# Архитектура

- **Версия документа:** 4.1.0
- **Статус:** реализовано
- **Обновлено:** 2026-10-15

## Цель

Хранить переносимое описание сервисов рядом с каждым проектом и обнаруживать
проекты непосредственно на текущей машине без промежуточной машинной
конфигурации.

## Локальный каталог проектов

Launcher сканирует только непосредственные дочерние каталоги `~/Documents`.
Каталог считается проектом только при наличии корневого файла:

```text
~/Documents/<project>/launcher.json
```

Тип проекта, наличие Git, `README.md`, язык и структура исходников для runtime
не имеют значения. Вложенные `launcher.json` не обнаруживаются. Скрытые каталоги
пропускаются.

Проект с `enabled: false` не загружается. ID всех включённых проектов должны
быть уникальны в пределах каталога. Некорректная версия, JSON или повторяющийся
ID приводят к явной ошибке при запуске.

## Launcher в строке меню

При старте приложение:

1. открывает `~/Documents`;
2. находит непосредственные папки с `launcher.json`;
3. проверяет версию формата и уникальность ID;
4. разрешает относительную команду и рабочий каталог от корня проекта;
5. строит меню;
6. запускает только сервисы с `autoStart: true`.

Ручной `Start` запускает или перезапускает сервис и затем открывает его `url`.
Автоматический запуск браузер не открывает. Перед стартом сервиса с `port`
Launcher освобождает этот порт только от слушающего TCP-сервера; процессы
клиентов, подключённых к нему, не завершаются.

Стандартный вывод и ошибки дочернего процесса постоянно читаются и передаются в
системный лог с ID проекта и сервиса. Непрочитанный pipe не может заблокировать
длительно работающий сервис.

Конфигурация читается один раз при старте. После изменения проектного файла
Launcher нужно перезапустить; Scanner CLI делает это автоматически после
подтверждённой записи.

## Контроль выбранного сервиса

Сервис с явным `autoRestart: true` проверяется каждые 5 секунд. Владельцем
таймера, процесса и его перезапуска остаётся `ServiceProcess`. Ручной Stop
отключает контроль; обычный запуск снова включает его. Остальные сервисы
не получают автоматических перезапусков.

Неожиданный выход процесса вызывает повторный запуск. Для заданного `healthURL`
проверки HTTP начинаются после 60 секунд подключения; ответ 200 с JSON
`status: "ok"` или `status: "starting"` считается успешным. Ошибка, таймаут
3 секунды или другое состояние перезапускают процесс. Ответ старого запроса
не может перезапустить уже заменённый либо вручную остановленный процесс.
Автоматический контроль не открывает браузер.

## Scanner CLI

Scanner CLI — вспомогательная интерактивная утилита. Runtime от неё не зависит.
CLI умеет:

- предложить создание `launcher.json` для обнаруженного Python-кандидата;
- проверить существующие проектные файлы и пути;
- определить типовые локальные порт и URL без запуска исходников;
- показать эффективный каталог с абсолютными путями;
- перезапустить Launcher после фактического изменения.

CLI больше не создаёт машинные конфигурации.

## Удалённые проекты

`remote/remotes.json` независимо описывает уже запущенные сетевые сервисы других
машин. Launcher показывает их ссылками и не управляет удалёнными процессами.

## Поток данных

```text
~/Documents/<project>/launcher.json
                  |
                  | прямое сканирование при старте
                  v
             Launcher.app
                  |
                  +--> локальные процессы

remote/remotes.json
                  |
                  +--> сетевые ссылки в меню
```

## Источники истины

1. Проектный `launcher.json` — единственный источник локальных проектов и
   сервисов.
2. Относительные пути в проектном файле разрешаются от папки проекта.
3. `remote/remotes.json` — источник удалённых ссылок.
4. Файлы `configs/*.json` сохранены как история прежней архитектуры, но runtime
   их не читает.
5. Секреты, токены и учётные данные в этих JSON запрещены.
